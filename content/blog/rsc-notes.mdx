刚上手 App Router 的时候我很困惑：明明 SSR 已经能把 HTML 提前渲染好了，为什么还要再造一个 Server Component？

用了一段时间之后我的理解是：**它们解决的根本不是同一件事**。

## SSR 解决的是"首屏什么时候出现"

传统 SSR 的流程是这样的：

1. 服务端把整棵组件树渲染成 HTML
2. 浏览器拿到 HTML，先显示出来
3. 下载全部 JS，hydration，页面变得可交互

注意第三步 —— **整棵树的 JS 都要下载**。一个只用来展示日期的组件，也得把 `date-fns` 打进包里送到浏览器。

## RSC 解决的是"这段代码需不需要去浏览器"

Server Component 的代码**永远不会进客户端 bundle**。它在服务端执行完，输出的是渲染结果，不是代码。

这意味着可以直接在组件里读数据：

```tsx title="src/app/blog/page.tsx"
// 这是一个 Server Component —— 没有 'use client'
export default async function BlogPage() {
  // 直接 await，不需要 useEffect，不需要 loading 状态
  const posts = await getAllPosts();

  return <PostList posts={posts} />;
}
```

以前必须这样写：

```tsx
'use client';

function BlogPage() {
  const [posts, setPosts] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    fetch('/api/posts')
      .then((res) => res.json())
      .then((data) => {
        setPosts(data);
        setLoading(false);
      });
  }, []);

  if (loading) return <Spinner />;
  return <PostList posts={posts} />;
}
```

后者需要：一个 API 路由、一个 loading 状态、一次额外的网络往返，以及这些逻辑对应的全部 JS。前者一个都不需要。

## 实践下来的三条经验

<Note>
  下面是我在这个博客里实际用到的取舍，不是通用结论。
</Note>

### 1. 默认写 Server Component

不加 `'use client'` 就是 Server Component。只有真的需要 `useState`、`useEffect` 或事件处理时才加。

我这个站里只有四个客户端组件：顶部导航（滚动感知）、文章筛选（点击切换）、以及音乐播放器相关的两个。剩下全是服务端渲染的。

### 2. 把 `'use client'` 推到叶子节点

这条最容易踩坑。`'use client'` 会**传染**：一个组件标记为客户端，它 import 的所有组件都会被打进客户端 bundle。

所以不要在页面顶层加，而要在真正需要交互的那个小组件上加。

### 3. 服务端与客户端之间只传可序列化的数据

函数、`Date` 对象、`Map` 都传不过去。所以我的文章数据里日期存的是 ISO 字符串而不是 `Date`：

| 字段 | 类型 | 原因 |
| --- | --- | --- |
| `date` | `string` | 能安全跨边界传递，也能直接进 JSON |
| `readingTime` | `number` | 构建期算好，客户端不重复计算 |
| `content` | `string` | MDX 源码，在服务端编译 |

这个约束听起来烦，但它其实在提醒你：**能在服务端做完的事，就别推给浏览器**。

## 一句话总结

SSR 是"提前把 HTML 画好"，RSC 是"让一部分代码永远不必去浏览器"。

前者优化的是**时间**，后者优化的是**体积**。它们叠加使用，效果才最好。
